# Button spec-conformance tests — redesign

Date: 2026-09-01
Status: approved in brainstorming, pending implementation plan
Supersedes: `2026-08-31-button-spec-conformance-design.md`, sections 4 (rule IDs),
7 (rule triage), and the parts of 9 (coverage tooling) that read `md_design/button.md`
directly. Sections 1, 3, 6, 8, 10–12 of that document are unaffected and still apply.

## 1. What changed and why

After the original pilot shipped (branch `test/button-spec-conformance`, 10 tasks,
`md_design/button.md` edited in place with 42 embedded rule IDs), review of that
work raised three points:

1. `[DS]`-tagged rules are design-system governance — a single component test
   cannot verify them, and having 13 `[DS]`-only `it.todo()`s plus 5 spec-gap
   todos out of 42 rules overstated what this suite can meaningfully audit.
2. Test focus should be on `[CODE]`-tagged bullets — the rules a component
   test can actually enforce.
3. `md_design/button.md` must never be modified in any way — no IDs, no
   splits, no tag corrections. Rule IDs and grouping must live in a separately
   generated markdown file instead.

`md_design/button.md` has already been restored to its original, pristine
content (verified: zero `BTN-` references, 257 lines, matching the original).
This document redesigns the rule-ID mechanism and test scope around the three
points above.

## 2. Decisions from this round

| Decision | Choice | Rationale |
|---|---|---|
| Source spec | Never modified | Hard constraint from the user. `button.md` is read-only input from here on. |
| Rule IDs | Live in a generated file, not the source | Satisfies the constraint above while keeping the traceability the original design wanted. |
| Test scope | `[CODE]` and `[DS + CODE]` get real tests; pure `[DS]` gets none (not even a todo) | `[DS + CODE]` rules have a component-owned half that's genuinely testable (e.g. accessible-name enforcement, XL-as-default) — excluding them would drop real, currently-passing coverage for no benefit. Pure `[DS]` is authored guidance a component cannot verify by construction. |
| Pure `[DS]` visibility | Listed in the generated file, marked out-of-scope | Full traceability: every rule in `button.md` is accounted for somewhere, without cross-referencing the original spec to know why something has no test. |
| Generation method | A parser script, not hand authorship | `button.md` changes should regenerate the ID file deterministically. Hand-editing the generated file would reintroduce exactly the drift risk that IDs were meant to prevent. |
| File locations | Both generator and output stay under `ndw-ui-kit/src/tests/` | Consistent with the standing "everything authored lives in `src/tests`" rule from the original pilot. |
| Ambiguous bullets | Three explicit special lists, not silent heuristics | Untagged bullets, untestable-as-written bullets, and either/or-or-duplicate bullets are three distinct failure modes worth reporting separately, each fully auditable rather than inferred. |

## 3. Data flow

```
md_design/button.md  (untouched, forever — read-only input)
        │
        ▼  src/tests/tools/generate-rule-spec.ts
        ▼
src/tests/button/button.rules.md   (generated, committed, regenerable)
        │
        ▼  src/tests/tools/check-spec-coverage.ts  (now reads THIS file, not button.md)
        ▼
src/tests/button/*.spec.ts   (test titles reference IDs from button.rules.md)
```

`button.rules.md` is a build artifact with a human-reading purpose: checked
into git, regenerated by rerunning the generator whenever `button.md`
changes. The coverage script additionally re-runs the generator into a
throwaway buffer and diffs it against the committed file — if they differ,
`button.md` changed since the last generation and `button.rules.md` is stale.
This is a new, stronger guarantee the original design didn't have: it isn't
enough for `button.rules.md` to look internally consistent, it must also
still match its source.

## 4. `button.rules.md` format

```markdown

generator instead. If a fresh run produces a diff, `button.md` changed
and this file is stale.

## Legend

- **[DS]** — out of scope: design-system governance a single component
  test cannot verify. Listed for traceability, not tested.

  set of color tokens for background, content, and stroke...
- **BTN-CLR-02** `[CODE]` (button.md:95) — Disabled uses dedicated
  disabled tokens...

## Typography (TYP)
...

## Layout (LAY)
...

## Elevation & Depth (ELV)
...

## Shapes (SHP)
...

## Variants (VAR)
...

## Composition (CMP)
...

## States (STA)
...

## Accessibility (ACC)
...

## Do's and Don'ts (DOD)
...

## Design-system governance — out of scope

Pure `[DS]` rules. Listed for traceability; none of these get a test.

- **BTN-CLR-03** `[DS]` (button.md:98) — `negative` status color is
  reserved for risky/destructive actions...
- **BTN-LAY-01** `[DS]` (button.md:112) — size guide: which size for
  which context...
...(all 14 — see §6.1 for the full list)

## Untagged bullets — spec defect

Bullets with no `[CODE]`/`[DS]`/`[DS + CODE]` tag in the source. Not
classified, not tested — see §6.2.

- (button.md:140) "Buttons otherwise sit flat on the surface; there is
  no resting elevation." — no tag in the source.

## Untestable as written — spec defect

Tagged rules that can't produce a single clean assertion because the
spec omits a value. See §6.3.

- **BTN-LAY-05** `[CODE]` (button.md:129) — padding: no values stated.
- **BTN-ELV-01** `[CODE]` (button.md:134) — drop-shadow: no value/token
  given.

## Ambiguous or duplicate bullets

Tagged rules that can't produce a single clean assertion because they
state two acceptable outcomes, or restate another rule. See §6.4.

- **BTN-SHP-03** `[CODE]` (button.md:153) — either/or: "transparent or
  token-driven per state" — two acceptable outcomes.
- **BTN-DOD-03** `[DS + CODE]` (button.md:251) duplicates **BTN-ACC-01**
  (button.md:223) — the accessible-name rule stated twice.
```

Every entry carries a `(button.md:N)` back-reference. Section order and
names mirror `button.md`'s own sections (Colors, Typography, Layout,
Elevation & Depth, Shapes, Variants, Composition, States, Accessibility,
Do's and Don'ts) so a reader can cross-reference either direction.

## 5. ID scheme

Unchanged in shape from the original design: `BTN-{SECTION}-{NN}`, same ten
section codes (CLR/TYP/LAY/ELV/SHP/VAR/CMP/STA/ACC/DOD). What changes is
where the ID lives (generated file, not the source) and which bullets get
one:

- `[CODE]` and `[DS + CODE]` bullets get an ID, always, in their section.
- Pure `[DS]` bullets get an ID too (so they're addressable in the
  out-of-scope list and in any future discussion), but no test is ever
  written against them.
- Untagged bullets get **no ID** — ID assignment is section-scoped, and a
  bullet with no tag can't be mechanically assigned a section without
  guessing. It appears in the "untagged bullets" list by source line only.

IDs are assigned once, in document order within each section, and are
permanent — the same rule as before.

## 6. Generator mechanics (`generate-rule-spec.ts`)

The generator is a mechanical parser wherever possible. Three known
irregularities need explicit, auditable handling instead of silent
inference:

### 6.1 Pure `[DS]` bullets

Mechanical: any bullet tagged exactly `[DS]` (bullet-level or, per §6.5,
heading-level) is routed to the "design-system governance" list with an ID,
not a test.

Full list (14), each `(button.md:N)`:

| ID | Line | Rule |
|---|---|---|
| BTN-CLR-03 | 98 | `negative` colour reserved for risky/destructive actions |
| BTN-LAY-01 | 112 | Size guide — which size for which context |
| BTN-VAR-02 | 164 | Primary — use / don't use |
| BTN-VAR-03 | 168 | Secondary — use / don't use |
| BTN-VAR-04 | 171 | Tertiary — use / don't use |
| BTN-VAR-05 | 175 | Ghost — use / don't use |
| BTN-VAR-06 | 178 | Negative status — use / don't use |
| BTN-VAR-07 | 182 | Positive status — use / don't use |
| BTN-VAR-08 | 186 | Warning status — use / don't use |
| BTN-VAR-09 | 190 | Documented negative/critical usage list |
| BTN-ACC-02 | 228 | `aria-pressed` belongs to a consumer owning toggle state |
| BTN-DOD-01 | 248 | Exactly one primary per screen or modal |
| BTN-DOD-02 | 249 | Don't use tertiary/negative for frequent actions or deletion |
| BTN-DOD-05 | 255 | Open item — `positive`/`warning` not exposed as coded variants |

Line 255 ("Open item for ndw-ui-kit...") is the one bullet in the document
that does not start with a leading `[TAG]` marker — see §6.7 for how its
primary tag (`[DS]`, giving `BTN-DOD-05`) is determined mechanically. This
table has 14 rows, not the original pilot's 13: `BTN-DOD-02` (line 249,
"don't use tertiary/negative...") was already correctly in the original
pilot's DS-only bucket, unchanged here. What's new is `BTN-DOD-05` itself —
the original pilot filed the open item under `[SPEC GAP]` instead of `[DS]`;
this redesign reclassifies it here because its primary tag (§6.7) is `[DS]`,
not because the original was a bug.

### 6.2 Untagged bullets

Mechanical detection (a bullet with no `\[CODE\]`/`\[DS\]`/`\[DS \+ CODE\]`
anywhere in its text), **no automatic classification**. One known case:

- (button.md:140) "Buttons otherwise sit flat on the surface; there is no
  resting elevation."

This is reported as a spec defect (missing tag) and nothing more. **No test
is written for it** — this is a deliberate scope reduction from the original
pilot, which had tagged it `[CODE]` itself and tested it (`BTN-ELV-03`,
previously passing: `box-shadow: none`, `filter: none`). Since we no longer
touch or reinterpret the source, a bullet the source itself left untagged
does not get promoted into a rule by us. If this coverage is wanted, the fix
belongs in `button.md` (out of scope for this tool) — recorded as a finding
rather than worked around.

### 6.3 Untestable as written

Mechanical detection is not possible here (recognizing "no value is given"
requires reading the prose); this is a curated table in the generator
script, each entry citing its source line and reason:

```ts
const UNTESTABLE_AS_WRITTEN = [
  {
    line: 129,
    id: 'BTN-LAY-05',
    reason: 'states "its own padding" with no values',
  },
  {
    line: 134,
    id: 'BTN-ELV-01',
    reason: 'states "subtle drop-shadow (filter)" with no value or token',
  },
];
```

Both bullets keep their tag-derived ID (they're still `[CODE]` rules) and
are routed to the "untestable as written" list instead of the main
per-section list that expects a real test.

Note line 129 is the same bullet that states the fixed-height values (also
testable, `BTN-LAY-04`) — the generator does **not** split this bullet the
way the original design did. One bullet, one ID (`BTN-LAY-05`), covering the
whole bullet's text; its testable height claim is `BTN-LAY-04` from a
different bullet on the same line range. Splitting a single source bullet
into two IDs would mean inventing structure not present in the text, which
is exactly what "don't reinterpret the source" rules out. (See §6.6 for why
this bullet parses as one bullet, not two, in the first place.)

### 6.4 Ambiguous or duplicate bullets

Also a curated table, combining both root causes the user confirmed should
share one list:

```ts
const AMBIGUOUS_OR_DUPLICATE = [
  {
    line: 153,
    id: 'BTN-SHP-03',
    kind: 'either-or',
    reason: '"transparent or token-driven per state" — two acceptable outcomes, can\'t assert one',
  },
  {
    line: 251,
    id: 'BTN-DOD-03',
    kind: 'duplicate',
    reason: 'restates BTN-ACC-01 (button.md:223) — the accessible-name rule',
    duplicateOf: 'BTN-ACC-01',
  },
];
```

Line 153 is itself a two-claim bullet, same shape as line 129 (§6.6): "All
variants use a 1px border" (universal, testable) and "ghost/tertiary render
it transparent or token-driven" (either/or, not testable). The generator
splits it the same way it splits line 129 — `BTN-SHP-02` (the border claim)
stays a normal per-section rule with a real test; only `BTN-SHP-03` (the
either/or clause) is routed here. `BTN-DOD-03` keeps its tag-derived ID and
is routed to this list instead of the main per-section list; nothing else
in its bullet is split out, since the whole bullet is one restated claim.

### 6.5 Heading-level tags

Mechanical rule, no curation needed: a `###` heading carrying its own
`[TAG]` is checked for tagged bullets in its own section (up to the next
heading of the same or higher level).

- **Has tagged children:** the heading tag is redundant with what its
  children already state — skipped, no ID. Applies to `### Composition —
  [DS + CODE]` (line 203, children are `BTN-CMP-01`/`BTN-CMP-02`) and
  `### States — [CODE]` (line 211, children are `BTN-STA-01..03`).
- **No tagged children (prose/table only):** the heading tag *is* the rule.
  Applies to `### Size guide... — [DS]` (line 112 → `BTN-LAY-01`) and
  `### Negative / critical status usage — [DS]` (line 190 → `BTN-VAR-09`).

### 6.6 Bullet boundaries

The generator treats each top-level `-` list item as one bullet, from its
start to the line before the next top-level `-` or the next heading,
including any wrapped continuation lines. Line 129's "Each size has a fixed
height... and its own padding and border radius (see Shapes)" is one bullet
by this rule (it's one `-` in the source, wrapping across two lines) —
which is why §6.3 treats it as a single untestable-as-written rule rather
than trying to carve out the height claim from within it. (`BTN-LAY-04`,
the height rule, comes from a **different**, earlier bullet — line 127,
"Each size has a **minimum button width**..." — which despite its own
wrapping is a separate `-` item stating both min-width and, in the original
design's reading, height. Re-reading the pristine source: line 127
states minimum width only; line 129 states height, padding, and radius
together. The generator therefore emits `BTN-LAY-04` from line 129 as
"has a fixed height" and separately routes the *same line's* padding/radius
clause through §6.3 as `BTN-LAY-05` — this is the one case where a single
bullet legitimately produces two IDs, because the bullet's own text lists
three distinct, independently-checkable claims (height, padding, radius),
not two alternative readings of one claim. This is a factual decomposition
of what the sentence enumerates, not an editorial rewrite.)

The same splitting applies to line 153 (§6.4): "All variants use a 1px
border; ghost/tertiary render it transparent or token-driven per state" is
one bullet stating two distinct, independently-checkable claims — a
universal border width, and a per-variant either/or. `BTN-SHP-02` (the
border claim) stays a normal, tested per-section rule; `BTN-SHP-03` (the
either/or clause) routes to the ambiguous/duplicate list. Lines 129 and 153
are the *only* two bullets the generator splits this way — every other
bullet in the document states exactly one claim.

### 6.7 Bullets without a leading tag marker

Every bullet in the document starts with `- **[TAG]**` or (in the Variants
section) `- **Label** — **[TAG]**` — a single, unambiguous tag right after
the dash. One bullet breaks this pattern: line 255, "**Open item for
ndw-ui-kit:** Figma defines `positive` and `warning` statuses that are not
currently exposed as coded variants. Flagged as **[DS]** design intent
pending a **[CODE]** decision on whether to surface them." It leads with a
bold label, not a tag, and contains *two* separate tags inline.

Mechanical rule: when a bullet has no tag immediately after its leading
dash, the generator takes the first `[TAG]` occurrence anywhere in the
bullet's text as its primary, classifying tag. For line 255 that's `[DS]`
(it precedes the inline `[CODE]` mention), so the bullet is classified as
pure `[DS]` and routed to governance as `BTN-DOD-05`. The later `[CODE]`
mention is not a second rule — same treatment as the Variants section's
intro sentence (line 173-174), where a second, later tag mention in the
same sentence does not get its own ID.

This rule has exactly one bullet to apply to; if a future spec edit adds
another tag-marker-less bullet, the same "first tag wins" rule resolves it
without needing a new special case.

## 7. Coverage script changes

`check-spec-coverage.ts` (from the original pilot) changes its input source
and gains one check:

- Parses `button.rules.md`'s own `**BTN-XXX-NN**` entries instead of
  scanning `button.md` for `[TAG] (ID)` patterns — the regex complexity from
  the original script (bold vs. plain tags, asterisk-adjacency, frontmatter
  exclusion) goes away, because the generated file's format is fully
  controlled and uniform.
- Every ID it finds must have a test or a todo, exactly as before.
- New: regenerates `button.rules.md` into memory and diffs it against the
  committed file. A mismatch fails the check with "button.rules.md is stale
  — rerun the generator" rather than silently coverage-checking an outdated
  file.

## 8. Test suite scope changes

- `button.todo.spec.ts` drops its `[DS] not enforceable by the component`
  describe block entirely — 13 todos removed, because pure `[DS]` rules are
  no longer part of the test suite's concern at all (they're visible in
  `button.rules.md`'s governance list instead).
- `[SPEC GAP] cannot be tested as written` shrinks to 2 entries (`BTN-LAY-05`,
  `BTN-ELV-01`) — down from 5, since the either/or and duplicate cases move
  to a new describe block.
- New describe block, `[AMBIGUOUS/DUPLICATE] two acceptable outcomes or a
  restated rule`: 2 entries (`BTN-SHP-03`, `BTN-DOD-03`).
- `[HARNESS LIMIT] well specified, not reachable by this tooling`: unchanged,
  1 entry (`BTN-STA-01` pressed).
- `button.geometry.spec.ts`, `.appearance.spec.ts`, `.behavior.spec.ts`,
  `.a11y.spec.ts`: unchanged in content — every test they contain targets a
  `[CODE]`/`[DS + CODE]` rule, which stays in scope. The one exception is
  `BTN-ELV-03` (resting elevation), removed per §6.2 since its source bullet
  has no tag.

Net: 21 real tests (was 22 — loses `BTN-ELV-03`; `BTN-SHP-02`, the
1px-border half of line 153, is unaffected and stays a real test), 3 todo
describe blocks totaling 5 entries — `[SPEC GAP]` 2 + `[AMBIGUOUS/DUPLICATE]`
2 + `[HARNESS LIMIT]` 1 (was 3 blocks / 19 entries), 14 rules visible only in
`button.rules.md`'s governance list, not the test suite at all (was 13 in the
original pilot — this redesign moves `BTN-DOD-05` there from `[SPEC GAP]`,
per §6.7's reclassification). 41 total addressable IDs
(was 42 — `BTN-ELV-03` no longer exists as an ID, only as an untagged-bullet
finding by source line): 21 real tests + 14 governance + 2 spec-gap +
2 ambiguous/duplicate + 2 dual test+todo (`BTN-STA-01`, `BTN-ACC-01`) = 41.
`BTN-STA-01`'s dual
status is real (the pressed sub-case is a genuine harness limit on an
otherwise-tested rule); `BTN-ACC-01`'s is an artifact of `BTN-DOD-03`'s todo
title mentioning "BTN-ACC-01" by name as a cross-reference to what it
duplicates — the coverage script's ID-in-title matching picks that up as a
todo reference even though ACC-01 itself is fully tested with no gap.

## 9. Findings carried forward unchanged

Both real code divergences from the original pilot (`BTN-DOD-04` — button
`type` attribute never actually set; `BTN-ELV-02` — focus-ring spread
mismatch) are `[CODE]`/`[DS + CODE]`-tagged rules, unaffected by this
redesign. `FINDINGS.md` needs its rule-ID cross-references double-checked
against the regenerated IDs (expected to be identical, since the ID scheme
didn't change — only *where* IDs are declared) but otherwise stands.

## 10. Self-review

- **Placeholder scan:** none found.
- **Internal consistency:** three numbering errors were caught and fixed
  during drafting, all against the pristine source or the actual committed
  code from the original pilot, not against assumption: (1) line 127 is
  min-width only, line 129 carries height + padding + radius together —
  `BTN-LAY-04` (height) and `BTN-LAY-05` (padding, untestable) both come from
  line 129, not two different lines as an earlier draft implied; (2) line 153
  splits the same way — `BTN-SHP-02` (border, tested) and `BTN-SHP-03`
  (either/or) both come from one bullet, and an earlier draft had these two
  IDs swapped; (3) `BTN-DOD-03` is the ACC-01 duplicate and `BTN-DOD-05` is
  the open item, matching the original pilot's own numbering — an earlier
  draft had both wrong, including a duplicate `BTN-DOD-03` label used for two
  different rules. §4, §6.1, §6.3, §6.4, and §8 now agree with each other and
  with the verified source line numbers.
- **Scope check:** single component (button), single generated file, single
  generator script, one modified coverage script. Fits one implementation
  plan.
- **Ambiguity check:** the "one bullet, two IDs" case in §6.6 is the one
  place this design deviates from "one bullet → one rule" — called out
  explicitly with its reasoning so an implementer doesn't read it as a
  contradiction of §5's general rule.

## 11. Open items

- `button.rules.md` is checked into git as a build artifact; if `button.md`
  is later edited (outside this session, since it's unversioned and
  external), the coverage script's staleness check will catch the drift on
  the next run — but nothing runs the generator automatically on a
  `button.md` change today. Acceptable for a single-component pilot;
  worth a pre-commit or CI hook if this scales to all four spec files.
- The existing branch `test/button-spec-conformance` already has 9 commits
  built on the old (in-source-ID) approach. This redesign will need new
  commits reworking Tasks 3/4/9/10's outputs; the implementation plan should
  treat this as amending/replacing specific files on the same branch, not a
  fresh branch, unless the user prefers otherwise.
